# 第 01 章：词法分析 —— 理论

> 词法分析（Lexical Analysis）是编译器的第一个阶段。它把字符流切成 **token 流**，让语法分析器不用再操心 `while` 是关键字还是标识符这种无聊问题。

## 1.1 词法分析器做什么

输入：`if (x >= 10) x = 0;`
输出（典型 token 流）：

```
IF      "if"
LPAREN  "("
ID      "x"
GE      ">="
INT     10
RPAREN  ")"
ID      "x"
ASSIGN  "="
INT     0
SEMI    ";"
```

每个 token = (类型, 属性)。
- **类型**：整数编码，方便后续比较（在 C 里通常是 `enum`）
- **属性**：字符串本身、数字字面值、行号（用于报错）

## 1.2 为什么不在语法分析阶段"顺手做"？

理论上可以（早期编译器确实这么干），但实际上：

| 问题 | 词法分离的好处 |
| ---- | -------------- |
| 性能 | 字符 → token 是热点，必须高效，单独优化 |
| 模块化 | 加新关键字不用动语法规则 |
| 错误定位 | "未闭合的字符串字面值"是词法错，`)` 应该是 `]` 是语法错 |
| 缓冲 | 词法器可以一次读一大块、做 lookahead；语法器拿到的是干净流 |

## 1.3 三种实现路线

### 路线 A：手写状态机

最朴素：根据当前状态和当前字符转移。`flex` 内部最终也是这个。

```c
// 简化的标识符识别
state S_START:
    if is_alpha(c) -> S_ID; consume
state S_ID:
    if is_alnum(c) -> S_ID; consume
    else -> emit TOK_ID; backup; reset
```

**优势**：可控、零依赖、错误信息最灵活。
**劣势**：写起来啰嗦，复杂词法（如字符串转义、注释嵌套）容易出 bug。

### 路线 B：表格驱动

把状态转移表预生成出来，运行期只查表。`lex` 输出的就是这种。性能极致，但生成的代码可读性差。

### 路线 C：正则表达式 + 工具

写正则，`flex`（或 Python 的 `re`、`Rust` 的 `regex`）帮你生成。
C/C++ 生态默认就是 **`flex`**。

> 我们课程主线走路线 C（flex）。路线 A 在第 4 章作为对照演示一次（手写递归下降的词法）。

## 1.4 正则语言与有穷自动机（理论骨架）

词法规则 = **正则表达式** = 描述一类字符串的紧凑写法。
正则表达式 = **有穷自动机**（FA）= 数学上等价的识别模型。

```
正则:  [a-z][a-z0-9]*
   ⇕
NFA:  ε转换 + 多个 ε-分支
   ⇓  子集构造
DFA:  每个状态对每个输入都有确定的下一个状态
```

**为什么重要**：
- 写正则很容易出错（顺序敏感、贪婪）
- 但 DFA 告诉你**有没有歧义** —— 有歧义就意味着这个文法不该写成词法
- flex 内部就是 NFA → DFA → 最小化，再生成代码

**C1 词法正则是 DFA 的好例子**：

```
keyword  : else|if|int|return|void|while
ID       : [a-zA-Z][a-zA-Z0-9]*
NUM      : [0-9]+
op       : +|-|*|/|==|!=|<|<=|>|>=|=|;|,|(|)|[|]|{|}|/*|*/
WS       : [ \t\n\r]+
COMMENT  : "/*" .*? "*/"
```

> 注意：正则不能描述嵌套结构（比如匹配的括号），所以**注释里的内容**不能精确用正则识别 —— 这就是为什么很多手写词法器对注释有特殊处理。

## 1.5 几个核心概念

### 1.5.1 最长匹配（Maximal Munch）

词法分析器总是匹配 **尽可能长** 的 token。
例：`ifoo` 一定识别成 ID，不会先识别成 `if` 再识别成 `oo`。

### 1.5.2 优先匹配（Rule Priority）

如果两条规则都能匹配同样长度，按 **规则定义的先后** 排优先级。
例：先写关键字，后写 ID。这样 `if` 优先匹配关键字，ID 只匹配非关键字的标识符。

### 1.5.3 Lookahead

少数情况下需要看 1 个字符之后才能决定。flex 通过 `yyless()` / `input()` / `unput()` 实现。

经典例子：C++ 的 `>>` vs `>` `>`，模板里 `vector<vector<int>>` 需要 lookahead 1。

## 1.6 现场常用方法的优劣

| 方法 | 适用场景 | 优势 | 劣势 |
| ---- | -------- | ---- | ---- |
| **手写状态机** | 性能敏感 / 错误信息要求高（V8、Clang 部分） | 控制力最强，可任意定制错误恢复 | 代码量大，难维护 |
| **flex + C** | 传统 C/C++ 项目、工具链成熟 | 几十年验证、生态完整（re2c、ragel 同类） | 生成代码大、与 C++ 集成略麻烦（C++ 用 re2c/boost::spirit 更顺） |
| **手写 + 缓冲优化** | 自研编译器 | 调试信息好、依赖少 | 教育意义大于实用价值 |
| **正则库（re2、hyperscan）** | 网络协议、敏感词、配置 | 表达力强 | 比 DFA 慢一个量级 |

**主流编译器现状**：
- GCC：手写
- Clang：手写
- V8：手写
- Rust：手写
- **Lua/Python 教学实现**：flex + bison

## 1.7 C1 文法的词法要求（来自参考文档）

[C1 文法见附录 A](../reference/c1-grammar.md)。词法上要注意：

| 类别 | 词素 | 类别 | 词素 |
| ---- | ---- | ---- | ---- |
| 关键字 | `else if int return void while` | 关系运算符 | `<= < > >= == != && \|\|` |
| 专用符号 | `+ - * / < <= > >= == != = ; , ( ) [ ] { } /* */` | 加法运算符 | `+ -` |
| 标识符 | `[a-zA-Z][a-zA-Z0-9]*` | 乘法运算符 | `* /` |
| 数字 | `[0-9]+` | 注释 | `/* ... */`（可跨行，不可嵌套） |

注意 `&&` 和 `&` 是两个不同 token（虽然 C1 没用 `&`），不能混。

## 1.8 小结与思考

- 词法 = 正则 → DFA → token 流
- 三种实现路线：手写、表格驱动、工具生成
- 现场主流是手写，但教学首选 flex
- C1 的词法规则很标准，适合入门

**思考题**：
1. 为什么 `if` 和 ID 不能用一条规则 `(if)|([a-zA-Z]+)`？提示：最长匹配。
2. 如果你写一个 JSON 解析器，应该用 flex 还是手写？为什么？
3. `/*` `*/` 这种注释如果嵌套（少数语言允许），flex 写得出来吗？
