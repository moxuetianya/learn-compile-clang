# 第 00 章：编译器全貌

> 这一章回答一个问题：当我点 `gcc main.c` 时，背后究竟发生了什么？

## 0.1 一句话回答

**编译器 = 把一种语言的程序翻译成"另一种等价形式"的程序**。
"另一种等价形式"可以是：

| 目标 | 例子 |
| ---- | ---- |
| 另一个编程语言 | `tsc`（TypeScript → JS） |
| 字节码（虚拟机执行） | `javac`、`kotlinc` |
| 中间表示（再交给后端） | `clang -emit-llvm` 输出 `.ll` |
| 目标机器码 | `gcc -c`、`rustc --emit=obj` |

我们这门课要做的是：**C1 语言子集 → LLVM IR → x86-64 机器码 → 可执行文件**。

## 0.2 经典划分

```
                    ┌─────────────────────────────────────────────┐
                    │              编译器                         │
源程序 (.c1) ────►  │  前端            中端            后端        │ ────► 目标程序
                    │  (Frontend)      (Optimizer)     (Backend)    │
                    │  词法/语法/语义   IR 优化          指令选择/    │
                    │  → AST           → IR            寄存器分配/  │
                    │  → IR                            汇编/链接    │
                    └─────────────────────────────────────────────┘
```

- **前端**：和源语言打交道。产出与源语言、与目标都无关的 IR。
- **中端（优化器）**：在 IR 上做等价变换。这一层通常与语言、目标都无关。
- **后端（代码生成器）**：把 IR 变成目标机器码。`clang` 给 `arm`/`x86`/`riscv` 出不同机器码靠的就是后端不同。

> 工业界为什么都这么做？**复用**。Clang 前端把 C/C++/ObjC 翻译成 LLVM IR 后，Apple/Intel/华为海思/RISC-V 厂商只要写各自的后端；优化 Pass 一次开发到处跑。1970 年代大家没意识到这点的时代，每个编译器都是从头到尾一个整体，改一个目标就重写一套。

## 0.3 LLVM 在哪一层

LLVM 不是"一个编译器"，它是一个 **编译器基础设施**，主要由三块组成：

| 组件 | 是什么 | 我们的课用在哪 |
| ---- | ------ | -------------- |
| LLVM IR | 一种 SSA 形式的中间表示 | 第 9 章手写 IR；最终输出 |
| LLVM Pass 框架 | 在 IR 上做变换/分析 | 第 11 章写常量折叠 |
| 各种后端 | x86-64/ARM/RISC-V/GPU… | 第 10 章用 `llc` 出汇编 |

我们使用 LLVM 的两种方式：

1. **生成 LLVM IR 文本**（`.ll` 文件），然后用 `llc` 编译到汇编，`as` 到目标文件，再 `ld` 链接。
2. **通过 C++ API**（`llvm::IRBuilder`、`llvm::Module`）直接在内存里构造 IR，调用 LLVM 的 JIT 或写出二进制格式。

第 9 章先走第 1 种（简单直观），第 10/11 章走第 2 种。

## 0.4 一个 Hello World 的"前 50 毫秒"

```bash
$ clang -v hello.c
```

能看到 clang 调用了：预处理器 → 编译器（前端+优化+后端） → 汇编器 → 链接器。
每一阶段其实都是 **独立的小程序** 通过临时文件协作。我们的课程编译器最后一章也会复用这个套路。

## 0.5 现场常见方案对比

| 场景 | 主流方案 | 为什么 |
| ---- | -------- | ------ |
| GCC/Clang 这种通用编译器 | 手写递归下降 + flex/bison 辅助 | 错误信息好、性能可控、长期维护 |
| TypeScript | 手写递归下降 | 错误恢复极其重要、增量编译 |
| Rust | 手写递归下降 + LALR 辅助 | 兼顾错误信息和歧义处理 |
| 玩具/教学语言 | flex + bison | 自动化、改文法快 |
| DSL/配置语言 | PEG ( Pest / peg.js) | 文法直观、易嵌入宿主语言 |
| JIT 场景 | LLVM ORC | 直接吃 IR，省去再写一遍后端 |

> 一句话：**手写 vs 工具生成的取舍 = 控制力 vs 开发速度**。本课程两种都教。

## 0.7 第一次实践：让 Clang 当老师

即使还没写自己的编译器，也可以用 `clang` 把 C1 风格的 C 程序翻译成 LLVM IR，看看后端长什么样：

```bash
$ cat <<'EOF' > /tmp/intro.c
int add(int a, int b) { return a + b; }
int main(void) {
    return add(40, 2);
}
EOF

$ clang -O0 -emit-llvm -S /tmp/intro.c -o /tmp/intro.ll
$ cat /tmp/intro.ll | head -40
```

你会看到：
- `@add` 和 `@main` 两个函数定义
- `i32` 表示 32 位整数
- `define ... { ... ret i32 ... }` 是 LLVM IR 的函数形式
- `%3 = add nsw i32 %2, %1` 这种 SSA 形式

这就是我们第 9 章要自己生成的东西。先有个直观印象。

## 0.8 小结与思考

- 编译器 = 前端 + 中端 + 后端
- 工具链复用是 LLVM 成功的关键
- 我们要做：`C1 → AST → LLVM IR → x86-64`
- 第一次实践：用 `clang -emit-llvm` 看一眼真实的 IR 长什么样

**练习**：
1. 用 `clang -emit-llvm -S` 把 `examples/hello.c` 翻译成 LLVM IR，标注出 `define`、`%xxx`、`ret` 三个语法点。
2. 想想：如果让你手动改写一个 `printf("hello")` 为 LLVM IR，你会写多少行？
