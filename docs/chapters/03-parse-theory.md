# 第 03 章：语法分析 —— 理论

> 词法把字符切成 token；语法分析把这些 token 组合成 **结构**。本章讲"结构"是什么，以及分析它的两类经典算法：自顶向下 vs 自底向上。

## 3.1 上下文无关文法（CFG）

语法 = 一组产生式。例：

```
program  → stmt_list
stmt_list → stmt_list stmt | ε
stmt     → if_stmt | while_stmt | assign | ...
if_stmt  → "if" "(" expr ")" stmt ["else" stmt]
expr     → expr "+" term | term
term     → term "*" factor | factor
factor   → "(" expr ")" | ID | NUM
```

记号：
- **终结符**（terminal）：词法切出的 token，如 `if` `+` `ID`
- **非终结符**（non-terminal）：语法变量，如 `expr` `stmt`
- **产生式**（production）：`A → α`，左边是非终结符，右边是符号串
- **起始符号**：第一个非终结符

CFG 之所以叫"上下文无关"：产生式应用只看非终结符本身，不看上下文。

## 3.2 推导、归约、解析树

**推导**（derivation）：从起始符号出发，反复挑一个非终结符，用它的产生式右边替换。

```
E ⇒ E + T ⇒ T + T ⇒ F + T ⇒ id + T ⇒ id + F ⇒ id + id
```

**归约**（reduction）：反过来，把右边归到左边的非终结符。

```
id + id ⇒ F + id ⇒ T + id ⇒ E + id ⇒ E + T ⇒ E
```

**解析树**（parse tree）：
- 根 = 起始符号
- 每个内部节点 = 一次产生式应用
- 叶子 = 终结符串
- 不同推导顺序可能产生 **不同的解析树**（如果文法有歧义）

## 3.3 歧义

一个句子有 **多棵解析树** = 文法有歧义。

经典例子：`if (a) if (b) s1; else s2;` 是匹配外层 if 还是内层 if？

> C 系语言的"else 匹配最近的 if"是约定，不是文法层面能解决的 —— 需要额外的消歧规则。

**怎么知道是否歧义？**
没有通用算法（不可判定）。但能构造反例，就能说"这文法歧义"。

**怎么去歧义？**
1. 改写文法（增加分层，如 `if_then` / `if_then_else`）
2. 给 bison/yacc 加优先级和结合性（见第 6 章）
3. 在语义层强制约束

## 3.4 左递归

直接左递归：`A → A α | β`
间接左递归：`A → B α`、`B → A β`

左递归 **会让递归下降分析器无限循环**。

> 为什么？递归下降 `parseA()` 第一步调用 `parseA()`，永远出不来。

消除方法（直接左递归）：

```
A → A α | β        ⇒    A  → β A'
                            A' → α A' | ε
```

C1 文法里到处都是左递归，例如 `additive_expression → additive_expression addop term`，第 6 章我们会用 bison 直接吃，**bison 不怕左递归**（LR 分析器能处理）。

## 3.5 提取左公因子

```
A → α β1 | α β2
```

预测分析时，`α` 这部分要"猜"用哪个产生式。

提取公因子：

```
A → α A'
A' → β1 | β2
```

## 3.6 语法分析的两大类

### A. 自顶向下（Top-Down）

- 从起始符号出发
- 反复**推导**出下一个 token
- 对应"预测分析"
- 实现：**递归下降**、LL(1) 表驱动
- **优点**：手工写直观、错误信息好
- **缺点**：难处理左递归、对文法限制多

### B. 自底向上（Bottom-Up）

- 从 token 流出发
- 反复**归约**出非终结符
- 对应"移进-归约"
- 实现：LR(0)/SLR/LR(1)/LALR 表驱动
- **优点**：分析能力强、能处理几乎所有程序语言文法
- **缺点**：表大、实现复杂；通常用工具（bison）生成

### 决策表

| 维度 | 自顶向下 (LL) | 自底向上 (LR) |
| ---- | ------------- | ------------- |
| 直观性 | 高 | 低 |
| 处理左递归 | 不行 | 行 |
| 文法要求 | 改写后能 LL(1) | 大部分文法都行 |
| 错误信息 | 好 | 中（bison 加 `%error-verbose` 后还行） |
| 实现复杂度 | 低 | 高 |
| 主流工具 | 手写 / ANTLR | bison / yacc |
| 工业代表 | TypeScript、Clang | GCC、Golang、Rust |

> **现场为什么很多用 LR/工具？**
> 1. 文法改写量小 —— 你能写出"自然"的产生式，工具帮你转成 LR(1)
> 2. 错误恢复机制成熟（bison 的 `error` token）
> 3. 对增量/容错需求不高的场景，LR 几乎是默认选择
>
> **那为什么 TypeScript 用手写递归下降？**
> 1. 错误信息是 TS 的生命线 —— IDE 里断点提示精确
> 2. 增量重解析需求大（你编辑一行，重解析的应该是局部）
> 3. 文法层就能控制歧义

## 3.7 LL(1) 预测分析

LL(1) = 从左（L）扫描、推导左边（L）、超前看 1 个 token。

**核心**：对每个非终结符 `A` 和每个 lookahead `t`，**恰好一个产生式可用**。

需要计算两个集合：

**FIRST(α)**：`α` 可能推导出的所有终结符串的首符号集合（含 ε）。

**FOLLOW(A)**：所有可能紧跟 `A` 出现的终结符集合。

预测分析表的构造：

```
M[A, t] = 产生式   当 t ∈ FIRST(α)
M[A, t] = A → α     当 ε ∈ FIRST(α) 且 t ∈ FOLLOW(A)
```

C1 文法做完这个表，你会发现很多格子是空的——说明 C1 **不是 LL(1)**（左递归太多、if-else 二义）。所以我们走 LR 路线。

## 3.8 LR(k) 家族

| 方法 | 含义 | 威力 |
| ---- | ---- | ---- |
| LR(0) | 不看 lookahead | 很弱，几乎只能分析很简单的文法 |
| SLR(1) | 简单 LR：用 FOLLOW 解决冲突 | 中等 |
| Canonical LR(1) | 完整 LR(1) | 最强，但表很大 |
| LALR(1) | lookahead 合并的 LR(1)，bison 默认 | 实践中 **最强性价比** |

第 5 章用 C1 子集做 LR(0) 推演，展示闭包/后继/项目集族是怎么算出来的。第 6 章直接用 bison 走 LALR(1)。

## 3.9 小结与思考

- 语法分析的核心数据结构：**CFG**
- 关键操作：推导 vs 归约
- 两条路线：自顶向下（递归下降/LL）和自底向上（LR/LALR）
- C1 文法有左递归，**走 LR 路线**（bison）
- 左递归消除、提取左公因子、计算 FIRST/FOLLOW 是基本功

**思考题**：
1. 写一个文法描述"中缀算术表达式 + - * / 括号"，自己判断是否歧义。
2. 算 `FIRST`/`FOLLOW`，画预测分析表。
3. 把这道题给 3 个同学，看谁的解析树能唯一 —— 如果不能，说明文法有歧义。
